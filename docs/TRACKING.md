## The three calls

```ts
track("step_done", { category: "funnel", props: { step_key, position } });
trackFailure("pdf_failed", err, { props: { kind: "plan" } });          // severity error, emailed
trackUnmet("unsupported_message", { props: { kind: "sticker" } });     // the owner's words come from the turn
```

- `category`: `behaviour`, `funnel`, `performance`, `failure`, `unmet_request`, `security`, `ops`.
- `severity`: `info` (default), `warn`, `error`, `critical`.
- `alert`: `none`, `digest` (the hourly email), `immediate` (within a minute).
  Defaults: `error`/`critical` → immediate; `warn` and every unmet request → hourly.
- `fingerprint`: repeats of the same problem become one incident. Defaults to
  the event name (plus the error class for `trackFailure`).

## Privacy rules (the code enforces them; do not work around them)

- **No phone number, ever.** The business id is stored. `internal` says whether
  the number is ours (`INTERNAL_WA_IDS`), and only the yes/no is kept.
- **An owner's own words go only in `excerpt`**: at most 200 characters, with
  phone numbers, emails and links stripped. `trackUnmet` takes them from the
  turn automatically.
- **Never put a token, login code, secret or full model prompt in `props`.**
  Request paths are stored with the connector token replaced (`/mcp/<token>`).
- **Logged errors keep their label only.** `console.error("model bad-json [x]: …")`
  is recorded as `model bad-json [x]`; error objects go through `errorText`
  (code and message only; a database error's failing row and a provider's
  error body never come along).
- **Charlie's own reply** in `apology_sent` is scrubbed like an owner's words,
  with any of the owner's words it echoed replaced by "[their words]", and is
  never copied onto the incident.
- **"Forget my business"** wipes `business_id`, `excerpt` and `turn_id` from that
  owner's events (`forgetBusiness`, and the `db/0024` trigger). What is left is
  anonymous, so the funnel still counts an owner who left.
- **Emails** show an owner as the first 8 characters of their id. Their words
  appear only in the hourly email of unmet requests, scrubbed as above;
  `ALERT_EMAIL_EXCERPTS=0` leaves them out.

## The emails

| Email | When | What |
|---|---|---|
| Immediate | At most every 5 minutes; the same problem at most every 30 minutes | Every new `error`/`critical` incident: a job that gave up, a plan build that failed, WhatsApp refusing a send, the model provider out of credit, a crashed request. |
| Hourly | Once an hour, if anything happened | Every time an owner tried something Charlie could not do, with what they said. Every warning. |
| Daily | `ALERT_DIGEST_HOUR_UTC` (default 05:00 UTC, 07:00 in Johannesburg) | Owners active and new, the funnel, questions, unmet requests, failures, plan build and reply times, model calls, failures and cost, WhatsApp send failures. |

Limits, so a long outage cannot run past Resend's free 100 a day: at most 60
immediate emails a day (after that, everything goes in the hourly one); each
email marks as sent only the count it reported, so a repeat counted while it
was being sent waits for the next one. The hourly window closes a minute
before it runs, so an event still being written lands in the next email,
never in neither. The daily summary claims a five-minute slot atomically and
is retried in the next slot until it goes; the day's counts (`event_daily`,
counted in SQL) are written first, whatever happens to the email. An unmet
request recorded with `alert: "none"` is counted but never sends an email on
its own.

Without `RESEND_API_KEY` + `ALERT_EMAIL_TO` nothing is sent and nothing is
marked sent. Incidents keep counting, `/admin` shows them, and the first email
after the key is set carries everything that waited.
